# Модель данных reChess

Этап 3. Схема реализована миграцией `backend/src/db/migrations/20261106000000_stage3_data_model.ts`, тестовые данные в `backend/src/db/seeds/01_dev_data.ts`, проверки в `backend/src/__tests__/schema.test.ts`. Открытые вопросы закрыты решениями из раздела «Принятые решения».

Источники: `docs/PLAN.md`, `docs/PROJECT_ANALYSIS.md`, миграция `20240713000000_init.ts`, живая БД `rechess`.

Не проверено: макет Figma, запрос снова отклонён лимитом тарифа Starter. От макета зависят список страниц и блоков, но это строки в таблицах, а не форма схемы.

## Исходное состояние

Факт, снято с БД 06.11.2026: MariaDB 11.8, InnoDB, `utf8mb4_unicode_ci`, 15 таблиц, 11 внешних ключей, применена только `init`. Все таблицы пусты, кроме `client`: 9 строк `Гость…` без e-mail и телефона, остатки тестов.

Вывод: переход безопасен, данных для переноса нет.

## Принципы

- Новая миграция поверх `init`, сама `init` не меняется.
- Названия таблиц и полей сохраняются, если нет причины менять. Новые следуют образцу: единственное число, `snake_case`, порядок задаёт `priority`.
- Деньги — целые рубли, как `price.price` и `sum` сейчас, проверка `Number.isInteger` уже в модели.
- Удаление мягкое: `deleted` во всех справочниках. В новых таблицах поле `NOT NULL`, в старых остаётся как есть. Журнал и связочные таблицы его не получают.
- Настраиваемое лежит в данных, секреты в окружении, структура страниц в коде.

## Связи

```
product ←─ price
   ↑
 item ──→ color (main_color, second_color)
   ↑ ↑ ↑
   │ │ └─ item_photo
   │ └─ cart_item ──→ cart ──→ client
   └─ order_item ──→ order ──→ client
                       ├──→ order_state
                       └──→ user (updated_by) ──→ role ←─ role_permission

shops ←─ shop_photo
page  ←─ page_block
page  ←─ seo (1:1)
user  ←─ publication (started_by)

Без связей: index_photo, seller, setting
```

## Что меняется в существующих таблицах

Жирным выделены новые поля.

| Таблица | Изменение | Почему |
|---|---|---|
| `item` | **`product_id`** FK, обязателен. Уникальность `(product_id, main_color, second_color)` | Пара принадлежит товару (ответ 1). Одна пара одного товара заводится один раз: удалённую CMS восстанавливает, а не создаёт заново |
| `price` | **`product_id`** FK, обязателен. Индекс `(product_id, price_date)`. `item` удалено | Цена привязана к товару. Текущая цена: последняя неудалённая с `price_date` не позже текущего момента. История и цены на будущую дату работают сами |
| `shop_photo` | **`shop_id`** FK на `shops`, обязателен | Фото принадлежат магазину (ответ 7) |
| `shops` | **`working_hours`** varchar(255), текст вида «Пн–Пт 10–20, Сб 11–18»; `start_working`, `end_working` удалены | Timestamp не подходит для часов работы (ответ 7), у магазинов часы по дням различаются |
| `seller` | **`name`** varchar(255), обязателен | CMS уже показывает эту колонку (В6) |
| `user` | **`role_id`** FK, обязателен | Роль из таблицы, а не из двух значений |
| `client` | **`delivery_point_code`** varchar(50). Убрать `comment` | Подстановка пункта выдачи рядом с подстановкой адреса. Комментарий переходит в заказ (ниже) |
| `order` | Новые поля в таблице ниже. Уникальность `number` | Номер видит покупатель, дубли недопустимы |
| `order_item` | **`price`** int, обязателен: цена за единицу на момент заказа | При нескольких товарах `order.sum` недостаточно (В7) |
| `cart` | У `sum` значение по умолчанию `0`. Индекс `last_updated` | Новая корзина пуста. Индекс для выборки брошенных корзин. `sum` — только значение для списка в CMS, цена всегда считается на бэке |
| `cart_item` | Уникальность `(cart_id, item_id)` | Двойной клик не создаёт две строки, повторное добавление увеличивает количество |

### Новые поля `order`

| Поле | Тип | Смысл | Основание |
|---|---|---|---|
| `name`, `family_name`, `city`, `phone`, `e_mail` | как в `client`; `name`, `phone`, `e_mail` обязательны | Снимок получателя | Заказов у клиента может быть несколько (ответ 5), а `client` перезаписывается при новом оформлении. Адрес снимком уже хранится, контакты должны идти с ним. Письма и СДЭК читают их из заказа |
| `delivery_point_code` | varchar(50), пусто при доставке до двери | Код пункта выдачи СДЭК | Ответ 10. Формат проверяется на этапе 8 |
| `delivery_cost` | int, пусто | Стоимость доставки, входящая в `sum`; пусто — не считалась или не входит в заказ | Принятое решение 3 |
| `payment_state` | varchar(32), обязателен, по умолчанию `not_paid` | Статус оплаты, только поле | План. Значения в коде: логику на них будет строить этап 11, это не справочник CMS |
| `comment` | varchar(1000), пусто | Комментарий покупателя | Ответы 5, 11 |
| `consent_at` | timestamp, обязателен, по умолчанию текущее время | Время согласия на обработку данных; этап 7 всё равно записывает его явно | План, этап 7 |
| `consent_version` | varchar(50), пусто | Редакция политики, с которой согласился покупатель; берётся из настройки `legal.consent_version` | Принятое решение 4 |

`sum` — итог к оплате по заказу: товары плюс `delivery_cost`, если доставка оплачивается в заказе.

Поля `delivery_address`, `address_delivery`, `delivery_reference`, `order_state_id`, `updated_by`, `last_updated` сохраняются со смыслом из В8 и В10.

## Начальные данные

В миграции, потому что без них система не работает на любой базе, в том числе боевой:

- `order_state`: Новый (10), Подтверждён (20), В производстве (30), Передан в доставку (40), Доставлен (50), Отменён (60). Новый заказ получает статус с наименьшим `priority`, поэтому поле `code` не нужно. Названия и порядок меняются в CMS.
- `role`, `role_permission`: вариант Б.
- `page`: `index`, `about`, `shop`, `colors`, `cart`, `privacy`, `personal-data`. `where-to-buy` удалена на этапе 10: «Где купить» — блок страницы магазина.
- `setting`: 16 ключей с пустыми значениями (сайт, контакты, счётчики, баннер, редакция политики, тексты писем). Список растёт с этапами.

В сидах (`npx knex seed:run`, в production отказывается работать), только для разработки: товар, цвета, пары, цены, продавец, магазины с фото, пользователи `admin` и `manager`, блоки страниц, SEO, клиент, корзина, заказ. Первый боевой админ создаётся отдельно: пароль не должен лежать в миграции, способ выбирает этап 4.

## Переход

Одна миграция с `up` и `down`. Порядок: новые таблицы и начальные данные, затем поля в существующих таблицах. `product_id` добавляется пустым, заполняется и становится обязательным, поэтому миграция не падает на непустых `item` и `price`. Для `shop_photo.shop_id` и `seller.name` значения взять неоткуда: на непустых таблицах миграция остановится с ошибкой, и это правильно.

9 строк `client` с открытыми токенами — тестовый мусор. Миграция их не трогает, локально они убираются вместе с запуском сидов.

В части 2 под схему обновляются модели и типы. Правки CMS, в том числе `tableSchemas.ts` и подпись «Товары» у пар, остаются этапам 4–5.

## Допущения

- Цена задаётся на товар: все пары одного товара стоят одинаково. Так записано в плане. Если пара получит свою цену, добавляется необязательный `price.item_id`.
- Артикул не хранится: он собирается из `color.code` (ответ 3). У второго товара с теми же цветами он совпадёт, поле кода товара добавится вместе со вторым товаром.
- Вопрос «А если это не шахматы?» отложен. `item.main_color` и `second_color` остаются обязательными, товар в один цвет схема не выражает.
- История смены статусов заказа не хранится, `updated_by` показывает только последнего. Этого не просили.

## Этап 8: доставка и письма

Миграция `20261107000000_stage8_delivery`.

- `delivery_tariff`: `name`, `address_delivery`, `city` (NULL — любой), `weight_to` (г, NULL — без предела), `price`, `priority`, `deleted`. Выбирается самый специфичный: тариф города раньше общего, затем меньший `weight_to`, `priority`, `price`.
- `product`: `weight_g`, `length_mm`, `width_mm`, `height_mm` (NULL = 0 для расчёта).
- `order`: `weight_g`, `delivery_tariff_id`, `confirmation_sent_at/error`, `track_sent_at/track_sent_ref/track_error`. Трек хранится в `delivery_reference`.
- Настройка `delivery.tracking_url`; значения по умолчанию для `mail.*`.

## Особенности реализации

- DDL в MariaDB не транзакционный, поэтому `down` написан на `IF EXISTS` и безопасен при повторном запуске после сбоя. Внешний ключ снимается раньше индекса, который он использует.
- `item (product_id, main_color, second_color)` уникален, включая удалённые строки: удалённую пару CMS восстанавливает.
- Пароли в сидах хешируются `scrypt` из `node:crypto`; окончательную схему хеширования выбирает этап 4.
- Тестовая БД: пользователь БД не может создавать новые базы, поэтому тесты идут на локальную `rechess`. Схемный тест пишет внутри транзакции и откатывает её; `client-api.test.ts` оставляет строки `client`, как и раньше.
